# アイドル状態の再定義: 休憩と思考の分離

## 問題

当初は「操作がなければアイドル状態にする」ことを最優先にした。アクティブ状態だけでは記録として役に立たないためである。しかし、入力イベントが無いという一点だけを見ると、「席を離れた休憩」と「入力せずに考えている時間」は区別が付かない。両方を`Idle`に一括すると、アイドル時間を「働いていない時間」として扱う下流の分析を歪める。

## 現状の実装

状態は`ActivityLog`の`String`フィールド(`src/main.rs:36`、enumではない)で、実質5値: `Active`・`AIConversation`・`DeepThinking`・`Idle`・`Away`。判定は最後の入力からの経過秒数`elapsed`のみに基づき、60秒バッチごとに評価される(`src/main.rs:283`)。

```
elapsed >= 1200秒                        -> Away
elapsed < 60秒 かつ 前面がAIサイト        -> AIConversation
elapsed < 60秒                            -> Active
elapsed >= 60秒 かつ 前面が仕事/読書用アプリ -> DeepThinking
それ以外                                   -> Idle
```

(`src/main.rs:284-294`。60・1200という閾値はインラインのリテラルで、名前付き定数でも設定可能でもない。)

休憩と思考を実際に分けているのは`DeepThinking`判定である。60秒以上操作が無いとき、前面ウィンドウのタイトルを許可リスト(`is_thinking_window`、`src/main.rs:134-165`。ブラウザ・エディタ・ターミナル・Obsidian・オフィスアプリ・AIサイト等)と照合し、該当すれば`Idle`ではなく`DeepThinking`として記録する。20分以上操作が無ければ、前面アプリに関わらず`Away`とする(それだけ長い無操作は、仕事用アプリが開いたままでも実質的な休憩とみなす)。

`AIConversation`は別枠で、直近60秒以内にAIウィンドウ内で入力があった場合に付く。チャットツールを開いただけ・タイプしただけで`Active`や`DeepThinking`に埋もれないようにするための区分(同じ閾値をプライバシー・集約境界の観点から記述しているのが`docs/adr/ADR-001-activity-data-boundary.md`)。

## この設計判断の実体

休憩と思考の区別は**内容(前面アプリが何か)で判定しており、時間の長さでは判定していない**。プレゼンスセンサーやカメラなど新規信号は一切使わず、タイトルそのものではなく、既存の「タイトルは記録しない、アプリ名にマッピングする」という仕組みを流用している。既存のプライバシー方針と一貫した設計になっている。

## 未解決のギャップ(この文書では直していない)

60秒〜20分の帯域内では、さらなる時間長による区分が無い。許可リスト内アプリでの90秒の間と18分の間は、どちらも同じ`DeepThinking`として記録される(`Idle`側も同様)。「これは仕事らしいか」には答えているが、「どれくらいの長さの間だったか」には答えていない。

下流では、`tools/aggregate_activity.py`が5状態を日次の分単位合計(`active_minutes`・`ai_conversation_minutes`・`deep_thinking_minutes`・`idle_minutes`・`away_minutes`)に圧縮し、アプリ由来の詳細(前面にあった具体的なアプリ名)はPCSに届く前に落ちる。この詳細レベルの情報が下流から観測できないのは事実。

**更新(2026-08-15):** ただし5状態の区別そのもの(休憩/思考の分離を含む)は、実際にはMeTheoryまで届いている。`deep_thinking_minutes`はPCSの`dev-pace-daily-v1`テンプレートの必須フィールドで、MeTheory側の`pcsSnapshotAnalysis.ts`がそこから`deep_thinking_ratio`を導出し、実際の相関分析の結果変数として使っている。この節は以前「伝わっていない」と書いていたが、それは古い記述だった。このドキュメントを鵜呑みにせずMeTheory側の実装を実際に読みに行ったことで、その比率の分母の計算に別の実バグがあることが分かった。詳細は`MeTheory-main-merge/docs/adr/ADR-016-total-observed-definition-ja.md`を参照。

## 却下した代替案

- **プレゼンス検知(カメラ・近接センサー)** — 新規センサーの追加とプライバシー方針の大きな変更に対して、得られる利益が見合わない。
- **OSのアイドルAPIのみ(前面ウィンドウ判定なし)** — まさに元々の問題そのもの。入力が0という点では休憩も思考も区別できない。
- **後から再分類するための全ウィンドウタイトルのログ保存** — 将来より良い状態判定ができる可能性はあるが、「タイトルは機微情報、アプリ名にのみマッピングする」という既存の境界(ADR-001)に反する。まだ実装が確定していない機能のために踏み越える理由がない。

## ステータス

レコーダー側の3帯域分類(アプリ許可リストによる区分)は実装済みで、休憩/思考の区別はPCS・MeTheoryまで実際に伝わっている(上記2026-08-15の更新を参照)。`DeepThinking`/`Idle`帯域内でのさらなる時間長分割は未実装のまま。意図的に保留しているだけで、忘れているわけではない。
